# RuoYi WMS 분석 및 재고 검증

원본: https://github.com/zccbbg/wms-ruoyi
프런트엔드: https://github.com/ShaunKR/RuoYi-WMS-VUE
분석 기준: ccc78f7 (master)

## 목적과 범위

오픈소스 WMS를 실행하고 입고·출고·재고 이력의 관계를 이해한다.
직접 개발한 범위는 별도 커밋과 검증 결과로 구분한다. 원본 시스템 전체를 직접 개발했다고 설명하지 않는다.

## 실행 구성

- Mac: Java 17 / Spring Boot 3.2.6, Node 20 / Vue 3 / Vite
- Docker: MySQL 8.4, Redis 7
- 학습 전용 DB: wms_portfolio. 원본 SQL은 이 DB에만 초기화한다.
- 컨테이너: shaunkr-wms-mysql (127.0.0.1:13316), shaunkr-wms-redis (127.0.0.1:16379)
- 프런트엔드 개발 서버: http://127.0.0.1:5175 (5173, 5174는 이미 사용 중)
- 백엔드: 8080. 연결 정보는 Git에서 제외되는 application-local.yml로 관리한다.

## 출고 코드 경로

`ShipmentOrderController.shipment` → `ShipmentOrderService.shipment` →
출고 전표·상세 저장 → `InventoryService.subtract` → 재고 이력 저장.

컨트롤러가 완료 상태를 설정하며 서비스의 `@Transactional` 경계 안에서
전표와 재고 및 이력을 처리한다. 실제 롤백 보장은 DB 통합 테스트로 별도 검증해야 한다.

## 초기 코드 관찰 (실행 검증과 구분)

- 재고가 없거나 계산 후 수량이 음수가 되면 부족 예외를 발생시키는 코드가 있다.
- 수량에 `@NotNull`은 있으나 양수 검증이 없으며, 상세 목록에 재귀 검증 `@Valid`가 없다.
- `subtract`는 현재 수량에서 요청 수량을 뺀다. 따라서 음수 요청은 재고 증가로 이어질 가능성이 있다.
- 조회 후 일괄 갱신하는 구조여서 동일 SKU·창고의 여러 상세 및 동시 요청은 추가 검증이 필요하다.
- 컨트롤러의 `@RepeatSubmit`만으로 완료된 전표의 영구적인 중복 처리 방지가 증명되지는 않는다.

## 검증 계획

| 시나리오 | 기대 결과 | 현재 상태 |
|---|---|---|
| 100개 입고 후 30개 출고 | 재고 70, 이력 일치 | MySQL 통합 테스트 통과 |
| 재고 10에서 11 출고 | 요청 거절, 재고 유지 | MySQL 통합 테스트 통과 |
| 음수·0·null 입출고 수량 | DB 변경 전 요청 거절 | 단위 테스트 8개 통과 |
| 같은 SKU를 2줄로 출고 | 누적 차감 및 부족 검사 | 미검증 |
| 완료 출고 재요청 | 중복 차감 방지 | 미검증 |
| 재고 10에서 동시에 7개씩 출고 | 한 건만 성공, 재고 3 | 미검증 |
| 처리 중 실패 | 전표·재고·이력 모두 롤백 | 재고 부족·음수 출고 실패 시 통합 테스트 통과 |

미검증 항목은 포트폴리오에서 완료했다고 표현하지 않는다.
