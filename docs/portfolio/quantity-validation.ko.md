# 개선 1: 입출고 수량 검증

## 문제

`InventoryService.subtract`는 `현재 재고 - 요청 수량`을 계산한다.
재고가 10일 때 요청 수량이 -3이면 결과가 13이 된다. 기존 부족 검사는 결과가 음수인지
확인하기 때문에 이 요청을 거절하지 않는다. 입고에도 0·음수·null 수량 검증이 필요하다.

## 수정

`add`와 `subtract`의 시작에서 상세 전체를 먼저 검사한다.
하나라도 null 상세, null 수량, 0 이하 수량이면 `ServiceException`을 발생시킨다.
전체 목록 검사를 먼저 수행하므로 앞쪽 정상 상세부터 부분 처리하지 않는다.
소수 양수(예: 2.5)는 기존대로 허용한다.

서비스 경계에 두어 HTTP 요청뿐 아니라 다른 서비스가 재고 서비스를 직접 호출할 때도
적용된다. 전표 저장 이후 재고 서비스에서 예외가 나는 경우 전표 트랜잭션의 롤백은
별도 MySQL 통합 테스트로 검증한다.

## 수정 전후 서비스 단위 테스트

테스트 파일: `ruoyi-admin-wms/src/test/java/com/ruoyi/wms/service/InventoryQuantityTest.java`

| 검증 | 수정 전 | 수정 후 |
|---|---|---|
| 입고 수량 null / 0 / -3 | 3건 실패 | 3건 통과 |
| 출고 수량 null / 0 / -3 | 3건 실패 | 3건 통과 |
| 앞 줄 정상, 뒤 줄 음수 | 실패 | 통과 |
| 정상 소수 출고 10 - 2.5 = 7.5 | 통과 | 통과 |
| 합계 | 8건 중 실패 7 | 8건 모두 통과 |

수정 전 null은 NullPointerException, 0·음수는 예외 없이 처리되어 기대 조건에 실패했다.
수정 후 잘못된 입력은 DB mapper 호출 전에 명시적인 서비스 오류로 거절된다.

## 범위와 한계

이 변경은 수량 검증 개선이다. 완료 전표 재처리, 동시 요청, 같은 창고·SKU의 중복 상세,
수량 소수 자릿수 제한은 별도 검증·개선 대상으로 남긴다. 이 변경만으로 재고 정합성 전체를
해결했다고 설명하지 않는다.

## 실제 MySQL 통합 테스트 결과

`WmsWorkflowIntegrationTest`: 3개 실행, 실패 0, 오류 0, 생략 0.

1. 입고 100 → 출고 30: 재고 70, 재고 이력 2건, 이력 수량 합계 70.
2. 입고 10 → 출고 11: 부족 예외, 재고 10 유지, 출고 전표·상세 없음, 입고 이력만 유지.
3. 입고 10 → 출고 -3: 검증 예외, 재고 10 유지, 출고 전표 없음, 입고 이력만 유지.

실제 Spring 트랜잭션 밖에서 사후 DB 상태를 조회했다. 테스트 자체를 하나의
롤백 트랜잭션으로 감싸서 실패를 가리는 방식은 사용하지 않았다.
